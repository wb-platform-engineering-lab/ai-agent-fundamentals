Core Concepts

AI Agent Engineering

How to design, build, and operate AI systems that reason, act, and learn — not just respond.

LLM Tool Use Multi-Agent Production

Overview

An AI agent is a system in which a large language model (LLM) drives a loop: it reasons about a goal, decides which action to take, executes that action via a tool, observes the result, and repeats — until the task is complete or it decides to stop.

This is fundamentally different from a standard LLM call, where you send a prompt and receive a single response. Agents are iterative, stateful, and action-capable. They can read files, call APIs, run commands, query databases, and make decisions based on intermediate results.

Key insight A regular LLM call is input → output. An agent is input → reasoning → action → observation → reasoning → action → ... → output. The loop is what makes it an agent.

The Problem: LLMs Alone Are Not Enough

Consider a software team that wants to automate code review. A naive approach: send the diff to an LLM and ask for a review. This works for simple cases, but breaks down immediately in production:

  • The diff references a function defined in another file — the LLM hasn't seen it
  • The team's coding standards are in an internal wiki — the LLM doesn't know them
  • The review should check for security patterns from last quarter's incident — not in training data
  • The comment should be posted to GitHub — the LLM can't do that
  • If one check fails, the LLM should try a different approach — it can't retry

An LLM without agency is a stateless oracle. It can reason but cannot act. It can answer but cannot adapt. AI agent engineering is the discipline of giving LLMs the tools, memory, and structure they need to be genuinely useful in production.

What is an AI Agent?

Three components are required:

🧠 LLM (the brain)

Reasons about the task, decides which tool to call, interprets results, and produces the final answer.

🔧 Tools (the hands)

Python functions the LLM can request to call. Each tool has a name, description, and input schema.

💾 Memory (the context)

What the agent knows: in-context history, retrieved documents, persisted state from prior sessions.

User message + tool definitions │ ▼ ┌─────────────┐ │ Claude │ ◄── system prompt + message history └──────┬──────┘ │ stop_reason? │ ┌─────┴──────┐ │ │ end_turn tool_use │ │ ▼ ▼ Final Dispatch answer tool │ ▼ Tool result │ ▼ Add to messages │ └──────► back to Claude

The loop runs until stop_reason == "end_turn" — meaning the LLM has all the information it needs and produces a final answer — or until a maximum step limit is reached.

Tool Use

Tool use is the foundational capability of all agents. Instead of returning text, Claude can return a structured tool call — a request to execute a specific function with specific arguments.

Anatomy of a tool definition

Every tool has two parts: a definition (what Claude sees) and an implementation (what your code runs).

# Definition — passed to the API
{
    "name": "run_git_diff",
    "description": "Returns the currently staged git diff.
                   Use this to see which lines are about to be committed.",
    "input_schema": {
        "type": "object",
        "properties": {
            "file_path": {
                "type": "string",
                "description": "Specific file to diff (optional)"
            }
        }
    }
}

# Implementation — your Python function
def run_git_diff(file_path: str = "") -> str:
    result = subprocess.run(
        ["git", "diff", "--staged"] + ([file_path] if file_path else []),
        capture_output=True, text=True
    )
    return result.stdout or "No staged changes found."
The description is the interface. Claude decides when and how to call a tool based purely on its description. A vague description like "this tool does stuff" means Claude won't know when to use it. A precise description means Claude uses it at exactly the right moment.

What the API response looks like when Claude calls a tool

{
  "stop_reason": "tool_use",
  "content": [
    {
      "type": "tool_use",
      "id": "toolu_01abc123",
      "name": "run_git_diff",
      "input": { "file_path": "auth.py" }
    }
  ]
}

Your code reads stop_reason, dispatches to the correct function, and sends the result back as a tool_result message. Claude never calls your functions directly — it returns a structured request, you execute it, you send back the result.

The Agent Loop

The agent loop is the core pattern used by every agent in this series. It is a while True loop that terminates when Claude returns stop_reason == "end_turn". 

def run_agent(user_message: str) -> str:
    messages = [{"role": "user", "content": user_message}]

    while True:
        # 1. Call Claude
        response = client.messages.create(
            model="claude-sonnet-4-6",
            tools=TOOL_DEFINITIONS,
            messages=messages,
        )

        # 2. Done?
        if response.stop_reason == "end_turn":
            return next(b.text for b in response.content if b.type == "text")

        # 3. Tool call — execute and send result back
        messages.append({"role": "assistant", "content": response.content})
        tool_results = []
        for block in response.content:
            if block.type == "tool_use":
                result = dispatch(block.name, block.input)
                tool_results.append({
                    "type": "tool_result",
                    "tool_use_id": block.id,
                    "content": result,
                })
        messages.append({"role": "user", "content": tool_results})
        # 4. Loop — Claude reasons with the tool result
Always add a MAX_STEPS guard. An agent without a step limit can loop indefinitely if the task is impossible or the tools keep failing. Set MAX_STEPS = 15 and return a graceful error if reached.

Memory

Agents have access to four types of memory, each with different scope and persistence:

Type Where it lives Scope Example
In-context Message history array Current session only Previous tool calls in this run
External (episodic) SQLite / database Persists across sessions Past standup notes, incident history
Semantic (RAG) Vector database (ChromaDB) Persists, retrieved by similarity Internal docs, past reports, code summaries
Parametric Model weights Fixed at training time General world knowledge

RAG — Retrieval-Augmented Generation

RAG solves the problem of domain-specific knowledge: instead of fine-tuning a model on your documents, you embed them into a vector database and retrieve the most relevant chunks at query time.

Query: "What's our password policy?" │ ▼ Embed query ──► vector [0.23, -0.11, 0.87, ...] │ ▼ ChromaDB similarity search │ ▼ Top 3 matching chunks from your docs │ ▼ Inject into Claude's prompt as context │ ▼ Claude answers with citation: "According to security-policy.pdf..."

The key principle: retrieval quality determines answer quality. The LLM can only answer as well as the chunks it receives. Chunk size, overlap, and embedding model choice all matter more than prompt engineering.

Core Patterns

ReAct — Reason + Act

The ReAct pattern makes the agent's reasoning visible before each action. Claude emits a text block (its thought) followed by a tool_use block (its action). This produces interpretable, debuggable agents.

User: "How many Python files are in this project?" Step 1 🧠 I need to count Python files. I'll use run_command. ⚡ run_command("find . -name '*.py' | wc -l") 👁 42 Step 2 🧠 I have the answer. ✓ "There are 42 Python files in this project."

Map-Reduce for Large Contexts

When a task involves more content than fits in one context window, split it into chunks (map), process each independently, then synthesize the results (reduce).

50 Python files (too large for one call) │ ▼ MAP (parallel Claude calls) file_1 → summary_1 file_2 → summary_2 Each summary: 3 bullets, ~100 tokens ... file_50 → summary_50 │ ▼ REDUCE (one final Claude call) all 50 summaries → answer to "where is the auth logic?"
Why this works: Summaries compress information — 500 lines of code becomes 3 bullets, losing noise but keeping semantics. The reduce step works because summaries preserve the meaning needed to answer most questions.

Multi-Agent Systems

A single agent handles one task at a time with one perspective. Multi-agent systems add specialization and parallelism: an orchestrator breaks a task into sub-tasks, delegates to specialist agents, and synthesizes their outputs.

┌─────────────┐ │ Orchestrator│ └──────┬──────┘ ┌───────────────┼───────────────┐ ▼ ▼ ▼ ┌──────────────┐ ┌──────────────┐ ┌──────────────┐ │ Security │ │ Performance │ │ Style │ │ Reviewer │ │ Reviewer │ │ Reviewer │ └──────┬───────┘ └──────┬───────┘ └──────┬───────┘ │ │ │ └────────────────┴────────────────┘ │ ┌─────▼──────┐ │ Synthesizer│ └────────────┘

Specialization is a system prompt choice — the same underlying model becomes a security expert or a style reviewer depending on the instructions it receives. No fine-tuning required.

PatternWhen to useTrade-off
Single agent Task fits in one context, linear workflow Simple, lower latency, lower cost
Parallel specialists Multiple independent perspectives needed Higher quality, higher cost, parallel latency
Sequential pipeline Each step depends on the previous output Modular, testable, additive latency
Hierarchical orchestration Complex tasks with many sub-tasks Flexible, harder to debug, highest cost

Human-in-the-Loop (HITL)

Production agents must know when to act autonomously and when to wait for human approval. The key principle: HITL gates belong in tool implementations, not in system prompts.

Prompt constraints can be bypassed. A system prompt that says "always ask before deploying" can be overridden by a cleverly phrased user message or an edge case the prompt didn't anticipate. A gate inside trigger_deployment() cannot be bypassed — it's code, not text. 
# ✗ Fragile — lives in the prompt, can be bypassed
SYSTEM_PROMPT = "Always ask for approval before deploying."

# ✓ Robust — lives in the tool, always enforced
def trigger_deployment(service: str, version: str) -> str:
    print(f"⚠️  Deploy {version} to {service}?")
    answer = input("Approve? [y/N]: ").strip().lower()
    if answer != "y":
        return "Deployment cancelled."
    return _deploy(service, version)
Action typeExamplesApproach
Safe Read file, search docs, query metrics Fully autonomous — no approval needed
Reversible Create draft, toggle feature flag, restart pod Autonomous, but log every action
Risky Send email, deploy to production, delete records Always require explicit human approval
Irreversible Database migration, billing charge, public post Require approval + confirmation + audit trail

Prompt Engineering

Prompt engineering is the discipline of writing instructions that produce reliable, precise, and consistent outputs — not just plausible-sounding ones. For production agents, this means treating prompts as code: versioned, tested, and iterated against real failure cases.

CCA-F Domain 4 — 20% of the exam. This domain tests your ability to write prompts with measurable criteria, apply few-shot examples, enforce structured output via tool schemas, implement retry loops, choose between synchronous and batch API patterns, and design multi-instance review architectures.

System prompt anatomy

A well-structured system prompt has four distinct layers:

┌───────────────────────────────────────────────────┐ │ 1. ROLE "You are a senior security reviewer." │ │ 2. CONTEXT "You are reviewing Python diffs in a │ │ fintech codebase. All user input is │ │ untrusted." │ │ 3. TASK "For each diff, identify vulnerabilities │ │ and call save_findings() with your results." │ │ 4. CONSTRAINTS "Only report issues in the ADDED lines (+). │ │ Do not flag commented-out code." │ └───────────────────────────────────────────────────┘

4.1 — Explicit criteria for precision

Vague instructions produce inconsistent outputs. The most common failure pattern: using qualitative language ("be conservative", "flag serious issues") that Claude must interpret differently each run.

✗ Vague — unreliable

"Flag any security issues you find. Be conservative and only report real problems."

Claude interprets "conservative" and "real" differently every run. False positive rate is unpredictable.

✓ Explicit — reliable

"Flag an issue ONLY if it meets one of these criteria:
— SQL query concatenated with unsanitized user input
— Secret or API key hardcoded as a string literal
— User-controlled data passed to eval() or exec()
Do NOT flag: commented-out code, test files, logging statements."

Explicit criteria reduce hallucination by giving Claude a decision boundary rather than a judgment call. The model matches against concrete patterns instead of estimating severity.

Vague instructionExplicit replacement
"Be thorough""Check every function in the diff, including helper functions"
"Flag serious issues""Flag issues with CVSS score ≥ 7.0 only"
"Return a short summary""Return exactly 3 bullet points, each under 15 words"
"Be conservative""If uncertain, set confidence: 'low' — do not omit the finding"

Few-Shot Prompting

Few-shot prompting provides 2–4 worked examples alongside the task description. Examples show Claude how to reason, not just what output shape to produce. They are the most effective tool for reducing hallucination in extraction tasks with varied input structures.

4.2 — When and why to use few-shot

Use few-shot when

  • Output requires nuanced judgment (not just format)
  • Input structure varies across documents
  • Zero-shot produces inconsistent tone or depth
  • Edge cases need explicit handling

Skip few-shot when

  • Task is unambiguous with explicit criteria
  • Output is purely structural (tool schema handles it)
  • Context window is already large
  • Examples would add confusion, not clarity

Anatomy of a good few-shot example

Each example should show: the input, the reasoning, and the output. The reasoning step is what enables generalization.

# System prompt excerpt with 2-shot examples

SYSTEM = """
Classify each support ticket by urgency: CRITICAL, HIGH, MEDIUM, or LOW.

Examples:

Input: "Our payment processor is returning 500 errors for all checkouts.
        We've lost $40k in sales in the last 20 minutes."
Reasoning: Revenue impact is immediate and quantified. Core business
           function completely broken. No workaround available.
Output: CRITICAL

Input: "The export to CSV button doesn't work on the reports page.
        I can still download via the API."
Reasoning: Feature broken but workaround exists. No revenue impact.
           Non-blocking for user's workflow.
Output: LOW

Now classify the following ticket:
"""
Example quality matters more than quantity. Two well-chosen examples that cover the hard judgment cases outperform six examples of obvious cases. Pick examples that represent the decision boundaries, not the easy middle ground.

Few-shot for extraction tasks

Extraction from varied document structures (invoices, contracts, incident logs) benefits especially from few-shot because the same field may appear in different positions or formats:

# Input 1: structured log
# "2026-05-19 14:32:01 ERROR auth-service pod/auth-7d9f CrashLoopBackOff"
# Output: { "service": "auth-service", "type": "CrashLoopBackOff", "time": "14:32:01" }

# Input 2: prose incident report
# "At around 2pm the authentication pod started restarting repeatedly"
# Output: { "service": "auth-service", "type": "CrashLoopBackOff", "time": "~14:00" }

Both inputs map to the same schema. Without examples, Claude might return different field names or omit the type entirely for the prose format. The examples teach the invariant mapping.

Structured Output via Tool Schema

Asking Claude to "return JSON" is fragile — the response might include markdown fences, explanatory text, or slightly wrong field names. A more reliable approach: define a tool whose input_schema is the exact JSON shape you want, then force Claude to call it.

1

Define the output schema as a tool

The tool's input_schema is your contract. Required fields, enum values, nested objects — all enforced at the API level before your code runs.

2

Force the call via system prompt

"Analyze the incident log and call save_incident_report with your findings. You MUST call this tool — do not write the report as text."

3

Read block.input, not block.text

The structured data is in the tool call's input dict — already parsed, already validated. No JSON parsing, no regex, no error handling for malformed output.

ApproachReliabilitySchema enforcement
"Return JSON" in promptFragileNone
response_format (OpenAI)MediumPartial
Tool schema (this approach)HighFull JSON Schema

tool_choice — controlling which tool is called

By default Claude decides whether to call a tool. You can override this with the tool_choice parameter:

ValueBehaviourWhen to use
{"type": "auto"}Claude decides — may call a tool or reply in textGeneral agent loops
{"type": "any"}Must call at least one tool; Claude picks whichForcing action, not known which
{"type": "tool", "name": "save_report"}Must call exactly this toolStructured output extraction

For structured output, always use tool_choice: tool pointing at your output schema tool. This guarantees stop_reason == "tool_use" and that block.input contains fully validated data.

response = client.messages.create(
    model="claude-opus-4-6",
    max_tokens=1024,
    tools=[{
        "name": "save_incident_report",
        "description": "Save structured incident report",
        "input_schema": {
            "type": "object",
            "required": ["severity", "affected_service", "root_cause"],
            "properties": {
                "severity":         {"type": "string", "enum": ["P1", "P2", "P3"]},
                "affected_service": {"type": "string"},
                "root_cause":      {"type": "string"},
                "remediation":     {"type": "string"},
                "recurrence_risk": {"type": "boolean"}
            }
        }
    }],
    tool_choice={"type": "tool", "name": "save_incident_report"},  # forced
    messages=[{"role": "user", "content": log_text}]
)

# stop_reason is always "tool_use" — safe to index directly
report = response.content[0].input
print(report["severity"])          # "P1" | "P2" | "P3" — guaranteed by enum
print(report["recurrence_risk"])    # True | False — guaranteed by type

Validation & Retry Loops

Even with tool schemas, extraction can fail when the source text doesn't contain the required information. The pattern: validate the output, and if it fails, send the error message back to Claude so it can correct itself.

┌─────────────┐ │ LLM call │ └──────┬──────┘ │ block.input ▼ ┌─────────────┐ PASS ┌───────────┐ │ Validate │ ───────────► │ Use data │ └──────┬──────┘ └───────────┘ │ FAIL ▼ ┌──────────────────────────────────┐ │ Append error as tool_result │ │ {"type":"tool_result", │ │ "content": "severity missing"} │ └──────────────┬───────────────────┘ │ ▼ retry (max 3×) ──► give up / raise
def extract_with_retry(text: str, max_retries: int = 3) -> dict:
    messages = [{"role": "user", "content": text}]

    for attempt in range(max_retries):
        response = client.messages.create(
            model="claude-opus-4-6",
            tools=[REPORT_TOOL],
            tool_choice={"type": "tool", "name": "save_incident_report"},
            messages=messages
        )
        data = response.content[0].input

        # Validate beyond what JSON Schema can check
        errors = validate_report(data)
        if not errors:
            return data

        # Feed the error back — Claude will try to correct
        messages += [
            {"role": "assistant", "content": response.content},
            {"role": "user", "content": [{
                "type": "tool_result",
                "tool_use_id": response.content[0].id,
                "content": f"Validation failed: {errors}. Please correct and retry."
            }]}
        ]

    raise ValueError(f"Extraction failed after {max_retries} attempts")
When retries don't help. If the source text simply doesn't contain the required information, retrying just wastes tokens and latency. Before retrying, check: is the information theoretically present in the input? If not, return a partial result or raise a clear exception — don't loop.
Failure typeRetry helps?Better approach
Wrong format (hallucinated field names)YesRetry with error feedback
Information absent in source textNoReturn partial result, flag gap
Ambiguous input (two valid interpretations)SometimesAsk for clarification first
Model confusion on complex schemaYesSimplify schema + retry

Batch Processing — Message Batches API

Every synchronous API call is billed at standard rates and competes for capacity. For workloads where latency doesn't matter — nightly report generation, bulk document processing, dataset annotation — the Message Batches API cuts cost by 50% at the expense of higher latency (results within 24 hours).

Use batches when
  • Latency tolerance > a few hours
  • Processing > ~20 requests
  • Nightly ETL, bulk annotation
  • Evaluation runs on test sets
  • Cost is the binding constraint
Use synchronous when
  • User is waiting for a response
  • Real-time agent loops
  • Interactive tools / chat
  • Low request volume
  • Latency is the binding constraint
import anthropic

client = anthropic.Anthropic()

# Submit up to 10,000 requests in one batch
batch = client.messages.batches.create(
    requests=[
        {
            "custom_id": f"doc-{i}",
            "params": {
                "model": "claude-opus-4-6",
                "max_tokens": 512,
                "messages": [{"role": "user", "content": doc}]
            }
        }
        for i, doc in enumerate(documents)
    ]
)
print(batch.id)  # msgbatch_01... — poll this later

# Poll until complete (in a separate job / cron)
while True:
    batch = client.messages.batches.retrieve(batch.id)
    if batch.processing_status == "ended":
        break
    time.sleep(60)  # check every minute

# Stream results — one result per custom_id
for result in client.messages.batches.results(batch.id):
    if result.result.type == "succeeded":
        print(result.custom_id, result.result.message.content[0].text)

Multi-Instance Review

When a single Claude instance reviews its own output, it tends to agree with itself — the same reasoning that produced the output also evaluates it. Running two independent instances — one to generate, one to review — catches errors the author misses.

┌─────────────────────────────────────────────────────────┐ │ Orchestrator │ └──────────┬──────────────────────────┬──────────────────┘ │ │ ▼ ▼ ┌─────────────────────┐ ┌─────────────────────────┐ │ Author Instance │ │ Reviewer Instance │ │ (no prior output) │ │ (sees author output, │ │ │ │ NOT author reasoning)│ └──────────┬──────────┘ └───────────┬─────────────┘ │ │ │ draft output │ review verdict └──────────────────────────►│ │ ▼ ┌─────────────────┐ │ approved / │ │ rejected+reason │ └─────────────────┘
def independent_review(task: str) -> dict:
    # Step 1: Author generates output (no self-evaluation)
    author_response = client.messages.create(
        model="claude-opus-4-6",
        system="You are an expert analyst. Perform the task thoroughly.",
        messages=[{"role": "user", "content": task}]
    )
    draft = author_response.content[0].text

    # Step 2: Reviewer evaluates — sees draft, NOT the author's chain of thought
    reviewer_response = client.messages.create(
        model="claude-opus-4-6",
        system="""You are a critical reviewer. Your job is to find errors,
gaps, and unsupported claims. Be skeptical. Do not assume correctness.""",
        messages=[{
            "role": "user",
            "content": f"Review this output for the task: {task}\n\nOutput to review:\n{draft}"
        }]
    )

    return {
        "draft": draft,
        "review": reviewer_response.content[0].text
    }
Why independent beats self-review
  • Author has no cached reasoning to anchor on
  • Reviewer system prompt enforces skepticism
  • Two model calls = two independent samples
  • Catches hallucinations author "knows" are right
Variations
  • Blind review: reviewer never sees the task, only output
  • Red team: reviewer actively tries to find failure modes
  • Majority vote: N reviewers, accept if >50% approve
  • Adversarial: debate format — author defends, reviewer attacks

State Machine Agents

Some workflows have enforced sequences. You can't promote a feature flag from draft directly to ga — that would bypass canary and rollout testing stages. When the agent's valid actions depend on current state, encode that as a state machine in your tool implementation.

draft ──► canary ──► rollout ──► ga ──► deprecated │ │ ▼ ▼ draft canary (rollback paths)
VALID_TRANSITIONS = {
    "draft":      ["canary"],
    "canary":     ["rollout", "draft"],
    "rollout":    ["ga", "canary"],
    "ga":         ["deprecated"],
    "deprecated": [],  # terminal
}

def transition_flag(name: str, to_state: str) -> str:
    current = get_flag_state(name)
    allowed = VALID_TRANSITIONS.get(current, [])
    if to_state not in allowed:
        return f"Error: '{current}' → '{to_state}' invalid. Allowed: {allowed}"
    # Claude reads this error, understands the constraint, and adapts
    ...

The agent doesn't need to know the rules upfront. It discovers them through tool responses — a failed transition returns an error message that tells Claude exactly what is allowed. This is more robust than encoding rules in the system prompt.

Model Context Protocol (MCP)

All patterns above use the Anthropic API directly — you write the tool definitions, the dispatch loop, and the agent logic. MCP flips this: you write a server that declares its tools, and any MCP-compatible client (Claude Code, Claude Desktop) can connect and use them — without any agent code on your part.

API tool useMCP server
Where tools liveIn your agent codeIn a separate server process
Who writes the loopYou (agent.py)The MCP client (Claude Code)
ReusabilityOne agent onlyAny MCP client
ConfigurationIn codeclaude_desktop_config.json
Tool definitionJSON schema dict@mcp.tool() decorator
 
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("git-tools")

@mcp.tool()
def get_staged_diff() -> str:
    """Returns the currently staged git diff.
    Use this to see which lines are about to be committed."""
    result = subprocess.run(["git", "diff", "--staged"], capture_output=True, text=True)
    return result.stdout or "No staged changes."

if __name__ == "__main__":
    mcp.run()

The docstring is the tool description — the same principle as API tool use, different syntax. Write it well.

Agents are harder to debug than regular software because their behavior is emergent. Every production agent needs structured logging of its decisions and actions.

Production Readiness Checklist

  • MAX_STEPS guard — every agent loop has an upper bound
  • Tool error handling — every tool returns a string error (never raises), so Claude can read and adapt
  • HITL gates in code — not in prompts, for any action with external side effects
  • Structured logging — every tool call logged with input, output, duration, error
  • Retry + backoff — transient API errors handled gracefully
  • Context budget management — load only the relevant subset of memory per run
